Large Language Models sind längst nicht mehr nur die Grundlage für Chatbots. Sie klassifizieren Texte, extrahieren Informationen, fassen Dokumente zusammen, durchsuchen interne Wissensdatenbanken oder erweitern bestehende Geschäftsprozesse um natürliche Sprache. Für Java-Teams stellt sich deshalb eine praktische Frage: Wie lässt sich ein LLM sinnvoll in eine bestehende Spring-Boot-Anwendung integrieren?

Der erste API-Call ist schnell geschrieben. Eine produktionsreife LLM-Integration in Spring Boot braucht aber deutlich mehr: Modellzugriffe müssen gekapselt werden, Prompts gehören nicht in Controller, Antworten sollten strukturiert verarbeitet werden, und Timeouts, Kosten, Observability und Fehlerbehandlung gehören von Anfang an dazu. In diesem Artikel zeige ich, wie ich eine LLM-Anwendung mit Spring Boot strukturiere und warum Spring AI dabei eine nützliche Abstraktionsschicht für bestehende Java-Backends ist.

## Warum Spring Boot für LLM-Anwendungen interessant ist

Viele Unternehmen betreiben bereits umfangreiche Systeme auf Basis von Java und Spring Boot. Darin stecken Geschäftslogik, Datenbankzugriffe, REST-APIs, Authentifizierung, Messaging und Monitoring. Eine neue KI-Funktion muss deshalb nicht als separate Python-Anwendung entstehen. Oft ist es sinnvoller, das LLM dort einzubinden, wo die Fachlogik bereits liegt.

Eine typische Architektur kann so aussehen:

```text
Frontend
   |
REST API
   |
Spring Boot Application
   |
Application Service
   |
AI Service
   |
Spring AI ChatClient
   |
LLM Provider
```

Entscheidend ist die Trennung der Verantwortlichkeiten. Das Sprachmodell ist keine neue Anwendungsschicht, die plötzlich die Geschäftslogik übernimmt. Es ist eine externe technische Abhängigkeit, ähnlich wie ein Payment-Provider, eine Suchmaschine oder eine andere externe API. Diese Sichtweise vereinfacht die Architektur erheblich.

## Spring AI als Abstraktionsschicht

Spring AI ist das Projekt des Spring-Ökosystems für generative KI. Es abstrahiert verschiedene Modellanbieter und bringt Bausteine für Chat Models, Embeddings, Vector Stores, Tool Calling, RAG, Chat Memory und Observability mit. Der `ChatClient` bietet eine Fluent API für Chat-Modelle und unterstützt synchrone wie Streaming-Aufrufe ([Spring AI Doku](https://docs.spring.io/spring-ai/reference/)).

Für diesen Artikel zählt vor allem eins: Die Anwendung arbeitet gegen eine gemeinsame Abstraktion statt gegen die API eines einzelnen Providers, und die Integration folgt den bekannten Spring-Konventionen. Unterschiede zwischen Modellen bei Kontextfenstern, Tool Calling, strukturierten Antworten und Kosten bleiben trotzdem bestehen. Die Abstraktion reduziert die technische Kopplung, sie beseitigt nicht die Eigenschaften des jeweiligen Providers. Wie sich Spring AI von LangChain4j unterscheidet, beschreibe ich im [Vergleich der beiden Frameworks](/blog/spring-ai-vs-langchain4j).

## Spring AI in Spring Boot einrichten

Für OpenAI stellt Spring AI einen eigenen Spring-Boot-Starter bereit. Zum aktuellen Setup gehört diese Maven-Dependency:

```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-openai</artifactId>
</dependency>
```

Die Versionen der Spring-AI-Module verwaltest du am besten über das offizielle BOM. Spring AI 2.0.x ist laut aktueller Dokumentation für Spring Boot 4.0.x und 4.1.x vorgesehen.

Der API-Key gehört nicht in den Code. Eine mögliche Konfiguration:

```yaml
spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
```

Der eigentliche Schlüssel kommt aus einer Umgebungsvariable oder einem Secret-Management-System:

```bash
export OPENAI_API_KEY=...
```

Damit konfiguriert Spring Boot die benötigten Komponenten automatisch.

## Der erste LLM-Aufruf mit ChatClient

Mit dem `ChatClient` ist ein erster Aufruf kompakt. Ein einfacher Service kann so aussehen:

```java
@Service
public class AiService {

    private final ChatClient chatClient;

    public AiService(ChatClient.Builder builder) {
        this.chatClient = builder.build();
    }

    public String generateAnswer(String question) {
        return chatClient
                .prompt()
                .user(question)
                .call()
                .content();
    }
}
```

Das funktioniert, für eine echte Anwendung würde ich aber nicht bei dieser Struktur bleiben. Der häufigste Fehler in neuen Java-Anwendungen mit generativer KI ist, dass der LLM-Zugriff über die gesamte Codebasis verteilt wird. Dann entstehen schnell Controller wie dieser:

```java
@PostMapping("/generate")
public String generate(@RequestBody String text) {
    return chatClient
            .prompt()
            .user("Analysiere folgenden Text: " + text)
            .call()
            .content();
}
```

Für einen Proof of Concept ist das akzeptabel, für eine langfristig wartbare Anwendung nicht.

## Eine bessere Architektur für Spring Boot und LLMs

Ich behandle die KI-Integration wie jede andere externe Infrastrukturkomponente. Eine mögliche Paketstruktur:

```text
com.example.application
├── customer
│   ├── CustomerController
│   ├── CustomerService
│   └── CustomerRepository
│
├── ai
│   ├── AiClient
│   ├── SpringAiClient
│   ├── PromptFactory
│   └── model
│
└── config
    └── AiConfiguration
```

Der Application Service muss Spring AI dann nicht kennen. Stattdessen definieren wir eine eigene Schnittstelle:

```java
public interface TextAnalyzer {

    AnalysisResult analyze(String text);
}
```

Erst die technische Implementierung verwendet Spring AI:

```java
@Component
public class SpringAiTextAnalyzer implements TextAnalyzer {

    private final ChatClient chatClient;

    public SpringAiTextAnalyzer(ChatClient.Builder builder) {
        this.chatClient = builder.build();
    }

    @Override
    public AnalysisResult analyze(String text) {
        // LLM Integration
    }
}
```

So bleibt die Fachlogik unabhängig vom konkreten KI-Framework, und das hat mehrere Vorteile: Tests werden einfacher, der LLM-Provider lässt sich austauschen, die Prompt-Logik liegt an einer definierten Stelle, und Spring-AI-APIs tauchen nicht unkontrolliert in der gesamten Anwendung auf.

## Prompts gehören nicht in den Controller

Prompts sind Teil der Anwendungslogik. Längere System-Prompts definiere ich deshalb nicht in einem REST-Controller, sondern zum Beispiel in einer eigenen `PromptFactory`:

```java
@Component
public class PromptFactory {

    public String createProductAnalysisPrompt(String description) {
        return """
                Analysiere die folgende Produktbeschreibung.

                Gib eine kurze Zusammenfassung und identifiziere
                die wichtigsten Produkteigenschaften.

                Produktbeschreibung:
                %s
                """.formatted(description);
    }
}
```

In komplexeren Anwendungen können Prompts auch als externe Ressourcen verwaltet werden. Dann lassen sie sich leichter versionieren, testen und ändern. Gerade in größeren Java-Anwendungen mit KI wird Prompt-Management schnell zu einem eigenen Thema.

### System-Prompt und User-Input voneinander trennen

Noch besser ist es, Instruktionen und Benutzereingaben nicht zu einem großen String zusammenzukleben. Spring AI unterscheidet verschiedene Message-Typen, über den `ChatClient` lassen sich unter anderem System- und User-Messages getrennt definieren:

```java
String result = chatClient
        .prompt()
        .system("""
                Du bist ein Assistent für die Analyse
                von Produktbeschreibungen.

                Antworte präzise und verwende ausschließlich
                Informationen aus dem bereitgestellten Text.
                """)
        .user(productDescription)
        .call()
        .content();
```

Diese Trennung macht die Absicht des Prompts klarer. Sie wird außerdem wichtig, sobald Eingaben aus externen Quellen kommen.

## Vermeide unstrukturierte LLM-Antworten

Ein weiterer häufiger Fehler: Das Modell produziert nur Text, und die Anwendung parst diesen Text anschließend von Hand. Angenommen, eine Anwendung soll Support-Nachrichten klassifizieren, und das Modell liefert:

```text
Kategorie: BILLING
Priorität: HIGH
Zusammenfassung: Kunde meldet eine doppelte Abbuchung.
```

Danach versucht der Java-Code, die einzelnen Werte mit String-Operationen herauszufiltern. Das funktioniert genau so lange, bis das Modell seine Formatierung ändert. Deutlich robuster sind strukturierte Antworten. Wir definieren zum Beispiel:

```java
public record TicketClassification(
        String category,
        String priority,
        String summary,
        double confidence
) {
}
```

Das Ergebnis lässt sich dann direkt als Java-Objekt verarbeiten. Spring AI konvertiert Modellantworten in strukturierte Typen, und aktuelle Versionen können zusätzlich providerseitige Structured Outputs und Schema-Validierung nutzen. Konzeptionell sieht das so aus:

```java
TicketClassification result = chatClient
        .prompt()
        .system("""
                Klassifiziere das Support Ticket.
                """)
        .user(ticketText)
        .call()
        .entity(TicketClassification.class);
```

Für Backend-Anwendungen ist das ein entscheidender Unterschied: Das LLM liefert nicht mehr nur Text für einen Menschen, sondern wird Teil eines maschinenlesbaren Workflows.

## Das LLM sollte keine Geschäftsregeln ersetzen

Eine der wichtigsten Architekturentscheidungen lautet:

> Welche Entscheidungen darf das Modell treffen und welche nicht?

Angenommen, ein LLM analysiert eine Kundenanfrage und stellt fest:

```text
Intent: CANCEL_SUBSCRIPTION
```

Die eigentliche Kündigung führt anschließend weiterhin deterministische Java-Logik aus:

```java
if (classification.intent() == CANCEL_SUBSCRIPTION) {
    subscriptionService.cancel(customerId);
}
```

So bleibt klar, welcher Teil probabilistisch und welcher deterministisch ist: Das LLM interpretiert Sprache, die Anwendung führt Geschäftslogik aus. Diese Trennung ist besonders wichtig bei finanziellen, sicherheitskritischen oder anderweitig sensiblen Prozessen.

## Tool Calling verbindet das LLM mit der Java-Anwendung

Interessant wird die Integration, wenn das Modell nicht nur Text erzeugt, sondern Funktionen der Anwendung nutzt. Ein Benutzer fragt zum Beispiel:

```text
Wie ist der Status meiner Bestellung 4711?
```

Das LLM kennt diesen Status nicht, die Anwendung hat ihn aber über einen `OrderService`. Hier kommt Tool Calling ins Spiel: Das Modell erkennt, dass es eine bestimmte Funktion braucht, die Java-Anwendung führt sie aus und gibt das Ergebnis zurück. Spring AI hat dafür eine eigene Tool-Calling-API. Mit dem `ChatClient` steuert der integrierte `ToolCallingAdvisor` den Ablauf ([Spring Blog](https://spring.io/blog/2026/06/12/spring-ai-2-0-0-GA-available-now/)).

Konzeptionell entsteht dadurch:

```text
User
 |
 v
LLM
 |
 | benötigt Bestellstatus
 v
Order Tool
 |
 v
OrderService
 |
 v
Database
 |
 v
Tool Result
 |
 v
LLM
 |
 v
Antwort
```

Das Sprachmodell wird so zu einer natürlichsprachlichen Schnittstelle für bestehende Java-Services.

### Tool Calling braucht klare Grenzen

Tool Calling ist leistungsfähig, erhöht aber auch das Risiko. Nicht jede Methode eines Spring-Service sollte automatisch als Tool verfügbar sein. Ich halte Tools bewusst klein, also zum Beispiel:

```text
getOrderStatus(orderId)
```

statt:

```text
executeDatabaseQuery(sql)
```

oder:

```text
executeCommand(command)
```

Das Modell sollte genau die Aktionen aufrufen können, die der jeweilige Anwendungsfall erfordert. Auch Spring AI weist bei der Tool Resolution darauf hin, dass eine zu breite automatische Tool-Verfügbarkeit sicherheitsrelevant sein kann. Es gilt dasselbe Prinzip wie bei normalen APIs: **Least Privilege.** Ein KI-Modell bekommt nicht mehr Rechte als unbedingt nötig.

## RAG für eigene Unternehmensdaten

Ein LLM kennt die internen Informationen eines Unternehmens nicht. Soll die Anwendung Fragen zu Dokumentationen, Verträgen, Produkten oder internen Prozessen beantworten, kommt deshalb häufig **Retrieval Augmented Generation** zum Einsatz, kurz RAG. Dabei sucht die Anwendung zuerst relevante Informationen und übergibt sie zusammen mit der Benutzerfrage an das Modell.

Eine typische Architektur:

```text
User Question
      |
      v
Embedding
      |
      v
Vector Store
      |
      v
Relevant Documents
      |
      v
Prompt + Context
      |
      v
LLM
```

Spring AI bringt dafür Vector-Store-Abstraktionen und Advisors für typische RAG-Abläufe mit. Der `QuestionAnswerAdvisor` implementiert ein einfaches RAG-Muster, der `RetrievalAugmentationAdvisor` ermöglicht modularere Retrieval-Abläufe ([Spring AI Doku](https://docs.spring.io/spring-ai/reference/)). So lässt sich eine bestehende Spring-Boot-Anwendung um semantische Suche oder dokumentenbasierte Fragen erweitern, ohne die Architektur neu aufzubauen. Wie das konkret aussieht, zeige ich Schritt für Schritt im [Spring AI RAG Tutorial mit PostgreSQL und pgvector](/blog/spring-ai-rag-java-tutorial).

## Fehlerbehandlung bei externen LLM-APIs

Ein LLM-Provider ist ein externer Service, und es können dieselben Probleme auftreten wie bei jeder anderen externen API:

- Netzwerkfehler
- Timeouts
- Rate Limits
- temporäre Provider-Fehler
- ungültige Antworten
- hohe Antwortzeiten

Spring AI hat konfigurierbare Retry-Mechanismen für Modellzugriffe, für die OpenAI-Integration etwa die maximale Zahl der Versuche und das Backoff-Verhalten. Trotzdem sollte nicht jeder Fehler automatisch zehnmal wiederholt werden. Für produktive Anwendungen lege ich fest:

- Welche Fehler sind transient?
- Wie viele Retries sind sinnvoll?
- Wie lange darf ein Request maximal dauern?
- Gibt es einen Fallback?
- Was sieht der Benutzer bei einem Fehler?

Besonders wichtig ist die maximale Gesamtlaufzeit. Ein HTTP-Request sollte nicht minutenlang blockieren, nur weil mehrere KI-Aufrufe hintereinander fehlschlagen.

## LLM-Calls gehören nicht zwangsläufig in synchrone Requests

Viele KI-Aufgaben dauern mehrere Sekunden. Für einen interaktiven Chat ist das meist akzeptabel, in klassischen Backend-Workflows kann es zum Problem werden. Sollen zum Beispiel 10.000 Produktbeschreibungen automatisch kategorisiert werden, würde ich nicht 10.000 Requests synchron über einen REST-Controller ausführen. Sinnvoller ist ein asynchroner Ablauf:

```text
REST API
   |
Job erstellen
   |
Message Queue
   |
Worker
   |
LLM
   |
Ergebnis speichern
```

Damit lassen sich Last, Retries und Fehler deutlich besser kontrollieren. Die eigentliche LLM-Integration bleibt dieselbe, nur die Ausführungsstrategie ändert sich.

## Streaming für interaktive Anwendungen

In Chat-Oberflächen kann Streaming die wahrgenommene Antwortzeit deutlich verbessern: Statt auf das vollständige Ergebnis zu warten, gehen bereits generierte Teile direkt ans Frontend. Der `ChatClient` von Spring AI unterstützt synchrone wie Streaming-Aufrufe. In klassischen Backend-Prozessen setze ich Streaming dagegen nur ein, wenn es einen konkreten Nutzen bringt. Nicht jede KI-Integration braucht einen Chat.

## Observability ist bei LLM-Anwendungen besonders wichtig

Bei normalen REST-APIs beobachten wir Antwortzeiten, Fehlerraten, Durchsatz und externe Requests. Bei KI-Anwendungen kommen weitere Fragen hinzu:

- Welches Modell wurde verwendet?
- Wie lange dauert ein Modellaufruf?
- Wie viele Tokens werden verbraucht?
- Welche Tools werden aufgerufen?
- Wie häufig schlagen strukturierte Antworten fehl?

Spring AI integriert sich dafür in die Observability-Funktionen des Spring-Ökosystems und liefert Metriken und Tracing unter anderem für `ChatClient`, `ChatModel`, `EmbeddingModel`, Advisors und Vector Stores. Für produktive Anwendungen ist das wichtiger, als es in vielen Tutorials wirkt, denn ein LLM-Call verursacht nicht nur Latenz, sondern häufig auch direkte variable Kosten.

## Kosten sollten Teil der Architektur sein

Bei einer klassischen Java-Methode spielt es meist keine Rolle, ob sie 500 oder 5.000 Zeichen verarbeitet. Bei einem LLM-Request macht genau das einen Unterschied: Mehr Kontext bedeutet in der Regel mehr Tokens und damit höhere Kosten und längere Verarbeitung. Deshalb kläre ich früh:

- Welche Informationen braucht das Modell wirklich?
- Wie groß dürfen Benutzereingaben sein?
- Wie viele Dokumente werden bei RAG geladen?
- Welches Modell ist für welchen Anwendungsfall nötig?

Nicht jede Aufgabe braucht das leistungsfähigste verfügbare Modell. Eine einfache Klassifizierung übernimmt oft ein kleineres Modell, komplexere Aufgaben ein stärkeres. In größeren Systemen wird Model Routing deshalb zu einem eigenen Architekturthema.

## LLM-Ergebnisse müssen validiert werden

Ein Sprachmodell ist keine deterministische Funktion. Selbst mit einem sehr guten Prompt kann eine Antwort falsch, unvollständig oder unerwartet sein. Die Anwendung sollte LLM-Ergebnisse deshalb nie automatisch als korrekt betrachten. Bei strukturierten Ergebnissen lässt sich zum Beispiel prüfen:

```java
if (result.confidence() < 0.8) {
    return manualReviewService.createTask(result);
}
```

Beachte dabei: `confidence` ist hier ein Wert, den das Modell selbst einschätzt. Er ist nicht kalibriert und taugt nur als grobes Signal. Verlässlicher ist die Kombination aus technischer und fachlicher Validierung. Die technische prüft etwa das JSON-Schema, die fachliche die Geschäftsregeln. Spring AI bietet für strukturierte Antworten inzwischen Schema-Validierung mit automatischen Wiederholungsversuchen, wenn eine Antwort nicht dem erwarteten Schema entspricht. Eine fachliche Validierung ersetzt das nicht.

## LLM-Provider hinter einer eigenen Abstraktion kapseln

Spring AI reduziert bereits die Abhängigkeit von konkreten Modellanbietern. In größeren Anwendungen definiere ich trotzdem zusätzlich eine eigene fachliche Abstraktion. Also nicht:

```java
public class CustomerController {

    private final ChatClient chatClient;
}
```

sondern zum Beispiel:

```java
public interface SupportTicketClassifier {

    TicketClassification classify(String ticket);
}
```

Der Rest der Anwendung muss dann weder wissen, dass OpenAI verwendet wird, noch dass es Spring AI gibt. Das erleichtert spätere Änderungen erheblich: Vielleicht nutzt die Anwendung heute OpenAI und morgen Azure OpenAI, Anthropic oder ein lokal betriebenes Modell. Vielleicht wird irgendwann sogar Spring AI selbst ausgetauscht. Die Fachlogik sollte davon möglichst wenig betroffen sein.

## Spring AI oder direkte OpenAI-Integration in Java?

Natürlich lässt sich OpenAI auch ohne Spring AI direkt aus Java ansprechen. Soll eine bestehende Spring-Boot-Anwendung aber um mehrere KI-Funktionen erweitert werden, bietet Spring AI handfeste Vorteile:

- Integration in die Auto-Configuration von Spring Boot
- einheitliche Model-APIs
- `ChatClient`
- strukturierte Outputs
- Tool Calling
- RAG und Vector-Store-Integration
- Advisors
- Observability
- Unterstützung verschiedener Provider

Spring AI lohnt sich besonders, wenn KI nicht ein einzelner API-Request bleibt, sondern dauerhafter Teil der Backend-Architektur wird. Für einen sehr kleinen Anwendungsfall reicht eine direkte Provider-Integration dagegen völlig aus. Ein zusätzliches Framework ist kein Selbstzweck. Falls du noch zwischen den Java-Frameworks schwankst: Spring AI und LangChain4j habe ich in einem [eigenen Vergleich](/blog/spring-ai-vs-langchain4j) gegenübergestellt.

Für eine größere LLM-Anwendung mit Spring Boot könnte die Architektur so aussehen:

Entscheidend ist nicht die genaue Zahl der Schichten, sondern dass das LLM sauber in die bestehende Architektur eingebettet ist.

## Best Practices für Spring Boot und LLMs

Wenn ich heute eine neue KI-Funktion in einer Java-Anwendung umsetze, sind mir diese Punkte besonders wichtig:

1. **LLM-Zugriff kapseln.** Der `ChatClient` sollte nicht quer durch Controller und Services verteilt sein.
2. **Prompts versionierbar halten.** Prompts sind Teil der Anwendungslogik und werden entsprechend behandelt.
3. **Strukturierte Outputs bevorzugen.** Java-Anwendungen arbeiten besser mit definierten Objekten als mit frei formatiertem Text.
4. **LLMs nicht für deterministische Logik verwenden.** Berechnungen, Berechtigungen und harte Geschäftsregeln bleiben in Java.
5. **Tool-Zugriffe begrenzen.** Ein Modell darf nur die Funktionen verwenden, die sein Anwendungsfall braucht.
6. **Timeouts und Retries definieren.** Ein LLM-Provider bleibt ein externer Dienst und kann ausfallen.
7. **Observability von Anfang an integrieren.** Latenz, Fehler und Kosten müssen sichtbar sein.
8. **Antworten validieren.** LLM-Output ist nie automatisch vertrauenswürdig.
9. **RAG nur einsetzen, wenn zusätzlicher Kontext nötig ist.** Nicht jede KI-Funktion braucht eine Vektordatenbank.
10. **KI als Teil der Architektur betrachten.** Der schwierige Teil einer produktiven KI-Anwendung ist selten der erste API-Call.

## Fazit

Eine LLM-Integration in Spring Boot kann erstaunlich einfach beginnen: Ein `ChatClient`, ein Prompt und ein Modell reichen, um in wenigen Minuten die erste Antwort zu erzeugen. Der Unterschied zwischen einer Demo und einer produktionsreifen Anwendung entsteht erst danach. Eine robuste Architektur braucht klare Verantwortlichkeiten, strukturierte Ergebnisse, Fehlerbehandlung, Observability, Sicherheitsgrenzen und eine saubere Trennung zwischen probabilistischer KI-Logik und deterministischer Geschäftslogik.

Spring AI liefert dafür inzwischen viele Bausteine, die sich gut in bestehende Spring-Anwendungen einfügen. Die Architekturentscheidungen nimmt das Framework dir aber nicht ab. Und genau darin liegt für mich der wichtigste Punkt: Ein LLM sollte nicht zum Mittelpunkt einer Spring-Boot-Anwendung werden, sondern ein gut gekapselter Bestandteil einer sauberen Backend-Architektur sein.

## Häufig gestellte Fragen zu LLMs und Spring Boot

### Wie integriere ich ein LLM in eine Spring-Boot-Anwendung?

Der einfachste Weg führt über Spring AI. Nach dem Einbinden des passenden Starters und der Konfiguration des API-Keys steht der `ChatClient` per Dependency Injection zur Verfügung. Für produktive Anwendungen solltest du den Modellzugriff anschließend hinter einer eigenen fachlichen Schnittstelle kapseln, damit Spring-AI-APIs nicht in der gesamten Codebasis auftauchen.

### Brauche ich für LLM-Anwendungen zwingend Python?

Nein. Für viele Anwendungsfälle ist Python keine Voraussetzung mehr. LLM-Integration, strukturierte Outputs, Tool Calling, Embeddings und RAG lassen sich direkt in einer Java-Anwendung umsetzen. Gerade wenn Geschäftslogik, Datenzugriff und Authentifizierung bereits in Spring Boot liegen, ist die Integration in Java meist der kürzere Weg.

### Wie bekomme ich strukturierte Antworten aus einem LLM?

Statt Text von Hand zu parsen, definierst du einen Java-Typ und lässt die Antwort direkt in dieses Objekt konvertieren. Spring AI unterstützt dafür Structured Outputs, zum Beispiel über `entity()` am `ChatClient`. Aktuelle Versionen können zusätzlich providerseitige Structured Outputs und Schema-Validierung nutzen.

### Wo sollten Prompts in einer Spring-Boot-Anwendung liegen?

Prompts gehören zur Anwendungslogik und nicht in einen REST-Controller. Sinnvoll ist eine eigene Komponente, etwa eine `PromptFactory`, oder die Verwaltung als externe Ressource. So bleiben Prompts versionierbar, testbar und an einer definierten Stelle.

### Ist Tool Calling ein Sicherheitsrisiko?

Tool Calling vergrößert die Angriffsfläche, weil ein Modell Funktionen der Anwendung auslösen kann. Deshalb gilt das Prinzip Least Privilege: Tools sollten fachlich eng geschnitten sein, etwa `getOrderStatus(orderId)` statt generischer Methoden wie `executeDatabaseQuery(sql)`. Berechtigungsprüfungen bleiben Aufgabe der Anwendung.

### Wann brauche ich RAG?

RAG brauchst du, wenn das Modell auf Informationen zugreifen soll, die es nicht kennt, zum Beispiel interne Dokumentationen, Verträge oder Produktdaten. Für Klassifizierung, Extraktion oder die Zusammenfassung eines mitgelieferten Textes ist keine Vektordatenbank nötig.

### Wie gehe ich mit Timeouts und Fehlern bei LLM-Providern um?

Ein LLM-Provider ist eine externe Abhängigkeit und kann ausfallen oder langsam antworten. Neben den konfigurierbaren Retry-Mechanismen von Spring AI solltest du vor allem eine maximale Gesamtlaufzeit festlegen. Außerdem sollte klar sein, welche Fehler transient sind, ob es einen Fallback gibt und was der Benutzer im Fehlerfall sieht.

### Sollten LLM-Aufrufe synchron im Request laufen?

Für interaktive Anwendungen ist ein synchroner Aufruf meist akzeptabel, oft ergänzt durch Streaming. Für Massenverarbeitung ist eine asynchrone Variante über Jobs und eine Message Queue deutlich robuster, weil sich Last, Retries und Fehler besser kontrollieren lassen.
